# دليل تكامل الباك إند مع خدمة Aoun AI

## 1. الغرض وحدود المسؤولية

هذا الملف هو العقد المرجعي لفريق الباك إند عند الاتصال بخدمة AI.

الباك إند الرئيسي مسؤول عن:

- مصادقة المستخدم وملكية المحادثة وRBAC.
- حفظ المحادثات والرسائل والملخصات في قاعدة البيانات.
- اختيار أقل بيانات مسموح بإرسالها إلى AI.
- تحديد متى يطلب تحديث ملخص المحادثة.
- حذف السجل الدائم وإبلاغ AI لمسح الذاكرة المؤقتة.

خدمة AI مسؤولة عن:

- بوابة السلامة وتحليل مقصد الرسالة.
- بناء طبقة ما قبل الاستعلام وإرسالها إلى OpenRouter.
- صياغة الرد وفق السياق المصرح.
- توليد ملخص عند طلب الباك إند.
- الاحتفاظ بذاكرة مؤقتة فقط ومسحها عند الطلب.

خدمة AI لا تتحقق من ملكية المستخدم للمحادثة؛ هذا التحقق إلزامي في الباك إند قبل
كل استدعاء داخلي.

## 2. حالة المكونات الحالية

| المكوّن | الحالة |
|---|---|
| OpenRouter عبر LangChain | منفذ، ويحتاج مفتاحاً حقيقياً في البيئة |
| Pre-query وسياسة السلامة | منفذ |
| تمرير ملخص المحادثة وآخر الرسائل | منفذ |
| endpoint إنشاء الملخص | منفذ |
| مسح ذاكرة المحادثة المؤقتة | منفذ |
| واجهة اختبار في `/` | منفذة وقابلة للتعطيل |
| كتالوج الأطباء والدورات من Public API | منفذ |
| FAQ والمحتوى النفسي العام عبر RAG | **غير منفذ بعد** |
| أدوات Agent للحجز والمواعيد | غير منفذة؛ تنتظر عقود الباك إند |

لا يجب اعتبار النموذج عارفاً بكل معلومات منصة عون حالياً. يعرف قواعد دوره، وما
يرسله الباك إند في السياق، ومحتوى المحادثة فقط. قسم "مصدر المعرفة" في هذا الملف
يحدد المطلوب لإضافة معلومات المنصة العامة بصورة صحيحة.

## 3. الاتصال داخل Docker

الباك إند يعمل كخدمة محلية على خادم Linux في `127.0.0.1:3000`. تستخدم حاوية AI
`network_mode: host` وتربط Uvicorn على `127.0.0.1:8000`. لا يستخدم Compose
`ports`، ولا يستمع AI على واجهة الشبكة العامة.

إعدادات الباك إند:

```env
AI_SERVICE_BASE_URL=http://127.0.0.1:8000
AI_SERVICE_TOKEN=the_same_value_as_AI_SERVICE_API_KEY
AI_SERVICE_TIMEOUT_MS=45000
```

اتجاه الاتصال:

```text
Main Backend -> 127.0.0.1:8000 -> Aoun AI
Aoun AI -> 127.0.0.1:3000 -> Main Backend Public API
```

هذا التصميم خاص بخادم Linux عندما يعمل الباك إند على host. إذا نُقل الباك إند
إلى حاوية لاحقاً، يجب العودة إلى Docker bridge network واستخدام اسم الخدمة بدلاً
من loopback.

## 4. الترويسات المشتركة

ترسل في كل endpoint تحت `/api/v1`:

```http
Content-Type: application/json
X-Service-Token: <AI_SERVICE_TOKEN>
X-Request-ID: <UUID generated by backend>
```

لا يرسل `AI_SERVICE_TOKEN` إلى المتصفح أو تطبيق الهاتف.

## 5. دورة المحادثة

```text
Client
  -> Main Backend authenticates user
  -> Backend verifies conversation ownership
  -> Backend stores user message
  -> Backend loads saved summary + recent uncovered messages
  -> Backend calls Aoun AI
  -> Backend stores assistant response
  -> Backend returns response to client
```

### Endpoint

```http
POST /api/v1/chat
```

### الطلب

```json
{
  "conversation_id": "018f73c0-7a5d-7aa1-9e02-123456789abc",
  "message": "ما زلت أشعر بالقلق بسبب الاختبار",
  "conversation_summary": "تحدث المستخدم سابقاً عن ضغط الدراسة وقرب الاختبار.",
  "recent_messages": [
    {
      "id": "msg-100",
      "role": "user",
      "content": "لدي اختبار الأسبوع القادم"
    },
    {
      "id": "msg-101",
      "role": "assistant",
      "content": "ما أكثر جزء يسبب لك الضغط؟"
    }
  ],
  "patient_profile": {
    "name": "أحمد",
    "age": 24,
    "gender": "male"
  },
  "medical_context": {
    "history": "سياق مختصر وافق المستخدم على استخدامه",
    "last_visit": "2026-07-20"
  }
}
```

قواعد الطلب:

- `conversation_id` يولده ويحفظه الباك إند، ولا يثق بقيمة من العميل دون فحص الملكية.
- `message` هي الرسالة الحالية ولا تكرر داخل `recent_messages`.
- `recent_messages` بحد أقصى 12 رسالة سابقة وبالترتيب الزمني.
- `conversation_summary` هو آخر ملخص محفوظ، أو `null` للمحادثة الجديدة.
- `patient_profile` و`medical_context` اختياريان ويحتويان أقل بيانات لازمة فقط.
- لا يرسل الملف الطبي الكامل أو أسرار أو بيانات لا يحتاجها الرد.

### الاستجابة

```json
{
  "conversation_id": "018f73c0-7a5d-7aa1-9e02-123456789abc",
  "response": "أفهم أن ضغط الاختبار ما زال يسبب لك القلق...",
  "status": {
    "intent": "support",
    "response_mode": "empathetic_support",
    "emotional_intensity": "elevated",
    "risk_level": "none"
  }
}
```

يحفظ الباك إند `response` كرسالة `assistant`. الحقول داخل `status` داخلية ولا
تعد تشخيصاً أو تقييماً سريرياً، ولا ينصح بعرض PID أو `emotional_intensity` للمستخدم.

## 6. تلخيص المحادثة

### من ينشئ ومن يحفظ؟

- **خدمة AI تنشئ الملخص.**
- **الباك إند يقرر وقت التلخيص ويحفظ النتيجة.**

لا يستدعى نموذج التلخيص مع كل رسالة. نقطة بداية مناسبة:

- بعد 10 إلى 12 رسالة جديدة منذ آخر ملخص؛ أو
- عندما يتجاوز مجموع محتوى الرسائل غير الملخصة 6000 حرف.

يستدعي الباك إند التلخيص بعد حفظ رد المساعد، ويفضل تنفيذه كعمل خلفي لا يؤخر رد
المستخدم.

### Endpoint

```http
POST /api/v1/conversations/{conversation_id}/summary
```

### الطلب

```json
{
  "existing_summary": "آخر ملخص محفوظ أو null",
  "messages": [
    {"id": "msg-102", "role": "user", "content": "..."},
    {"id": "msg-103", "role": "assistant", "content": "..."}
  ]
}
```

الحد الأقصى 12 رسالة في طلب تلخيص واحد.

### الاستجابة

```json
{
  "conversation_id": "018f73c0-7a5d-7aa1-9e02-123456789abc",
  "summary": "الملخص المدمج الجديد...",
  "covered_message_ids": ["msg-102", "msg-103"]
}
```

يخزن الباك إند:

- `summary`.
- آخر `covered_message_id` أو جميع المعرفات المغطاة حسب تصميم قاعدة البيانات.
- وقت تحديث الملخص وإصدار نموذج التلخيص إن احتاج التدقيق.

إذا فشل التلخيص، يبقي الباك إند الملخص السابق والرسائل غير المغطاة ثم يعيد
المحاولة لاحقاً. فشل التلخيص لا يحذف الرسائل ولا يعطل المحادثة.

## 7. حذف المحادثة

يبدأ الحذف من endpoint المستخدم في الباك إند. بعد التحقق من الملكية وحذف أو
تعطيل السجل الدائم، يستدعي الباك إند:

```http
DELETE /api/v1/conversations/{conversation_id}
```

الاستجابة:

```http
204 No Content
```

المسار idempotent؛ يمكن تكراره بأمان. في الإنتاج يفضل استخدام Outbox job أو حدث
`conversation.deleted` لإعادة محاولة تنظيف AI عند تعطل الخدمة مؤقتاً.

## 8. Health checks

```text
GET /health/live
GET /health/ready
```

- `live`: عملية FastAPI تعمل.
- `ready`: إعداد OpenRouter ومصادقة الخدمة جاهزان.

يستخدم Docker `/health/ready`. هذه endpoints لا تنفذ طلباً فعلياً مدفوعاً إلى
OpenRouter.

## 9. مثال عميل TypeScript للباك إند

```ts
type AiRole = "user" | "assistant";

interface AiRecentMessage {
  id: string;
  role: AiRole;
  content: string;
}

interface AiChatRequest {
  conversation_id: string;
  message: string;
  conversation_summary?: string | null;
  recent_messages: AiRecentMessage[];
  patient_profile?: Record<string, unknown> | null;
  medical_context?: Record<string, unknown> | null;
}

export async function requestAiReply(
  baseUrl: string,
  serviceToken: string,
  payload: AiChatRequest,
  requestId: string,
) {
  const response = await fetch(`${baseUrl}/api/v1/chat`, {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-Service-Token": serviceToken,
      "X-Request-ID": requestId,
    },
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(45_000),
  });

  if (!response.ok) {
    throw new Error(`AI service failed with status ${response.status}`);
  }

  return response.json();
}
```

في تطبيق حقيقي يجب تحويل أخطاء الاتصال إلى خطأ خدمة مناسب، وعدم تسجيل body لأنه
قد يحتوي بيانات نفسية حساسة.

## 10. رموز الأخطاء

| الرمز | المعنى | تصرف الباك إند |
|---|---|---|
| 200 | نجح الطلب | حفظ الرد |
| 204 | تم مسح الحالة أو لم تكن موجودة | اعتبار الحذف ناجحاً |
| 401 | مفتاح الخدمة غير صحيح | خطأ إعداد؛ لا تعاود عشوائياً |
| 404 | واجهة الاختبار معطلة أو مسار خاطئ | مراجعة URL |
| 422 | payload غير مطابق | خطأ عقد بين الخدمتين |
| 500 | فشل داخلي أثناء الرد أو التلخيص | تسجيل request ID وإعادة مناسبة |
| 503 | النموذج أو إعداد الجاهزية غير متاح | retry محدود مع backoff |

لا تسجل `message` أو `medical_context` في logs. سجل `X-Request-ID`، اسم endpoint،
زمن الاستجابة، والرمز فقط.

## 11. مصدر معلومات المنصة العام

### الحالة الحالية

تم ربط كتالوج المنصة العام الفعلي من:

```text
GET /api/doctors?page={page}&limit={limit}
GET /api/courses?page={page}&limit={limit}
```

تقرأ خدمة AI الأطباء والتخصصات والأسعار والجداول الأسبوعية العامة، كما تقرأ
الدورات المنشورة والفعالة وتصنيفها والطبيب وعدد الدروس. تستبعد الصور والحقول غير
اللازمة قبل بناء Pre-query.

الباك إند يعمل على host port `3000`. وبما أن حاوية AI تستخدم host networking على
خادم Linux، يستخدم الإنتاج:

```env
PLATFORM_API_BASE_URL=http://127.0.0.1:3000
PLATFORM_CATALOG_CACHE_TTL_SECONDS=300
PLATFORM_API_TIMEOUT_SECONDS=10
PLATFORM_CATALOG_MAX_ITEMS=100
```

تجلب الخدمة جميع الصفحات حتى حد العناصر، وتحتفظ بكاش لمدة 300 ثانية، ثم تمرر
أعلى 5 أطباء أو دورات مرتبطة بالسؤال فقط. إذا تعطل Public API تستخدم آخر نسخة
ناجحة، وإن لم توجد نسخة تتابع المحادثة من دون كتالوج.

`availabilities` جدول أسبوعي عام وليس موعداً مؤكداً قابلاً للحجز. يمنع Prompt
النموذج من اختلاق وقت أو تأكيد حجز قبل إضافة booking tool موثوق.

إدارة الكاش من الباك إند:

```text
GET  /api/v1/catalog/status
POST /api/v1/catalog/refresh
```

كلا المسارين يحتاج `X-Service-Token`. يمكن استدعاء `refresh` بعد نشر أو تعديل أو
حذف طبيب أو دورة؛ وإلا يتحدث الكاش تلقائياً بعد TTL.

هذا الكتالوج بيانات منصة حية، وليس قاعدة معرفة نفسية عامة كاملة. FAQ ومحتوى
التثقيف النفسي التفصيلي وسياسات المنصة ما زالت تحتاج مصدراً مستقلاً إن كانت مطلوبة.

إرسال كمية كبيرة من معلومات المنصة داخل كل `/chat` غير موصى به لأنه يرفع التكلفة،
يجعل المعلومات قديمة، ويضعف دقة النموذج.

### تصميم مصدر FAQ والمحتوى العام المستقبلي

```text
Backend Public API returning approved JSON (source of truth)
  -> AI validates schema and version
  -> in-memory/Redis cache with TTL
  -> lexical retrieval for a small first version
  -> top relevant approved snippets
  -> pre-query context
```

الباك إند يبقى مصدر الحقيقة. لا يرسل الملف كاملاً مع كل `/chat`؛ خدمة AI تجلبه
من Public API وتخزنه مؤقتاً، ثم تختار العناصر المرتبطة برسالة المستخدم. حتى لو كان
المسار اسمه Public API، يفضل أن تستخدم حاوية AI عنوان الباك إند داخل شبكة Docker:

```env
PLATFORM_KNOWLEDGE_API_URL=http://backend:3000/api/public/ai-knowledge
PLATFORM_KNOWLEDGE_CACHE_TTL_SECONDS=300
PLATFORM_KNOWLEDGE_REQUEST_TIMEOUT_SECONDS=10
```

إذا كان المصدر ملف JSON بدلاً من API، يستخدم العقد نفسه ويمكن تركيب الملف داخل
الحاوية read-only. لا نعتمد الخيارين معاً كمصدر حقيقة؛ API هو الموصى به، والملف
يمكن أن يكون fallback أو وسيلة اختبار.

### عقد Public Knowledge API المقترح

```http
GET /api/public/ai-knowledge?locale=ar
If-None-Match: "knowledge-version-or-etag"
```

الاستجابة:

```json
{
  "version": "2026-08-01.1",
  "updated_at": "2026-08-01T10:00:00Z",
  "items": [
    {
      "id": "platform-faq-booking",
      "title": "طريقة حجز جلسة",
      "category": "platform_help",
      "locale": "ar",
      "content": "المحتوى العام المعتمد...",
      "keywords": ["حجز", "جلسة", "موعد"],
      "version": 3,
      "status": "published",
      "updated_at": "2026-08-01T10:00:00Z"
    }
  ]
}
```

متطلبات endpoint:

- يعيد عناصر `published` فقط.
- يدعم `ETag` و`If-None-Match` حتى لا ينقل JSON دون تغيير.
- يستخدم UTF-8 و`application/json`.
- يضع حداً لحجم الاستجابة وعدد العناصر.
- يبقي `id` ثابتاً ويرفع `version` عند تعديل المحتوى.
- لا يحتوي بيانات مستخدمين أو سجلات طبية أو أسرار.
- حذف عنصر من المصدر يجب أن يزيله من snapshot التالي.

سلوك خدمة AI المطلوب عند التنفيذ:

1. تجلب snapshot عند أول حاجة أو عند بدء الخدمة.
2. تحتفظ بآخر نسخة ناجحة لمدة TTL.
3. بعد انتهاء TTL ترسل `If-None-Match`؛ استجابة `304` تمدد صلاحية النسخة.
4. إذا تعطل الباك إند تستخدم آخر نسخة ناجحة ولا تمنع المحادثة.
5. إذا لم توجد أي نسخة ناجحة، تتابع المحادثة بلا معرفة عامة وتظهر الحالة في logs.
6. تمرر للنموذج أعلى 3 إلى 5 عناصر مرتبطة بالسؤال فقط مع `source_id` و`version`.

للمحتوى الصغير نبدأ باسترجاع لفظي عربي مع `keywords`. عندما يكبر المصدر أو تصبح
الأسئلة دلالية أكثر، نضيف embeddings وVector Store من دون تغيير عقد Public API.

كل وثيقة معرفة يجب أن تملك عقداً مثل:

```json
{
  "id": "platform-faq-booking",
  "title": "طريقة حجز جلسة",
  "category": "platform_help",
  "locale": "ar",
  "content": "المحتوى العام المعتمد...",
  "version": 3,
  "status": "published",
  "reviewed_by": "authorized-reviewer-id",
  "reviewed_at": "2026-08-01T10:00:00Z",
  "updated_at": "2026-08-01T10:00:00Z"
}
```

المحتوى المناسب للفهرسة:

- تعريف المنصة وخدماتها.
- طريقة الاستخدام والحجز والإلغاء.
- الأسئلة الشائعة والسياسات العامة.
- محتوى تثقيف نفسي عام راجعه مختصون.
- قنوات التواصل والمساعدة البشرية المعتمدة.

المحتوى غير المناسب للفهرسة:

- بيانات المرضى والمحادثات.
- المواعيد والأسعار المتغيرة لحظياً إذا كانت موجودة في قاعدة الباك إند.
- الأسرار والمفاتيح والبيانات الداخلية.
- مسودات غير منشورة أو محتوى لم يراجعه مسؤول معتمد.

المعلومات الحية مثل المواعيد وحالة الحجز تجلب مستقبلاً عبر Agent tools من الباك
إند، ولا تؤخذ من RAG.

### المطلوب قبل تنفيذ مصدر FAQ المستقبلي

يحتاج فريق المنصة إلى توفير:

1. الرابط الداخلي الفعلي لـPublic API.
2. عينة JSON حقيقية من الاستجابة.
3. من يملك صلاحية اعتماد ونشر المحتوى.
4. سياسة تحديث وحذف الوثائق.
5. الحجم التقريبي للاستجابة وعدد العناصر المتوقع.

لا نحتاج اختيار Vector Store قبل النسخة الأولى. بعد توفر الرابط والعينة يمكن تنفيذ
عميل Public API والكاش والاسترجاع وربطه بـPre-query. إلى ذلك الحين يجب ألا يدعي
الباك إند أن AI يقرأ قاعدة معرفة المنصة.

## 12. قائمة تحقق الباك إند

- [ ] الباك إند يستمع محلياً على `127.0.0.1:3000`.
- [ ] `AI_SERVICE_BASE_URL=http://127.0.0.1:8000`.
- [ ] `AI_SERVICE_TOKEN` محفوظ كسر خادمي.
- [ ] ملكية المحادثة تتحقق قبل كل chat/summary/delete.
- [ ] الرسائل وردود AI تحفظ في قاعدة البيانات.
- [ ] التلخيص يعمل كخلفية ولا يؤخر المستخدم.
- [ ] حذف المحادثة يرسل purge إلى AI مع retry موثوق.
- [ ] logs لا تحتوي نصوصاً أو سياقاً طبياً.
- [ ] الباك إند يسمح للحاوية بالوصول إلى Public API على host port `3000`.
- [ ] يستدعى `/api/v1/catalog/refresh` بعد تغييرات الكتالوج المهمة أو يقبل TTL.
- [ ] مصدر FAQ والمحتوى النفسي العام محدد ومراجع قبل تفعيل RAG.
