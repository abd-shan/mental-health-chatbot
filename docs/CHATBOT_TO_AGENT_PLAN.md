# خطة نقل خدمة عون من Chatbot إلى Agent

## 1. الهدف

الهدف ليس جعل النموذج يتحدث أكثر، بل تحويله من مولّد ردود إلى منسّق مهام يمكنه:

- فهم مقصد المستخدم وحاجته الحالية.
- استرجاع معلومات مسموح بها من باك إند عون.
- اختيار أداة مناسبة ضمن صلاحيات محدودة.
- طلب تأكيد المستخدم قبل أي عملية تغيّر البيانات.
- تسليم المحادثة إلى إنسان عند الحاجة.
- إنتاج سجل تدقيق واضح من دون تخزين سلسلة التفكير الداخلية.

الـAgent لا يشخّص، ولا يصف دواءً، ولا يتخذ قراراً سريرياً، ولا يتصل بالطوارئ
بشكل مستقل.

## 2. طبقة ما قبل الاستعلام

يجب ترتيب كل استدعاء للنموذج بهذا التسلسل:

1. **السياسة الثابتة:** الهوية، الحدود، السلامة، أولوية التعليمات.
2. **خطة الدور:** المقصد، نمط الرد، شدة النبرة غير السريرية، وأهداف الدور الحالي.
3. **السياق المصرح:** أقل بيانات لازمة فقط، وموسومة كبيانات غير موثوقة.
4. **ملخص المحادثة:** حقائق وقرارات سابقة، لا نسخ كامل غير محدود للمحادثة.
5. **رسالة المستخدم الحالية:** توضع كرسالة مستخدم مستقلة ولا تدمج في system prompt.
6. **عقد المخرجات:** رد مباشر للمستخدم أو قرار أداة من مخطط بيانات معروف.

التنفيذ الحالي في `prompting.py` يغطي السياسة وخطة الدور والسياق وعقد المخرجات.
كما تستقبل الخدمة ملخصاً محفوظاً في الباك إند ورسائل حديثة، وتوفر endpoint مستقلاً
لتحديث الملخص بعد عدد محدد من الرسائل.

## 3. تقوية الاستنتاج من دون كشف Chain of Thought

لا نعتمد على عبارة عامة مثل "فكر خطوة بخطوة". البديل هو خط أنابيب قابل للقياس:

```text
Safety gate
  -> deterministic intent and turn plan
  -> allowed-context retrieval
  -> structured action decision
  -> policy and permission gate
  -> tool execution when allowed
  -> response composition
  -> output safety review
```

قرار التخطيط المستقبلي يكون بنية داخلية مثل:

```json
{
  "intent": "booking",
  "risk_level": "none",
  "needs_tool": true,
  "tool_name": "list_available_slots",
  "arguments": {
    "specialty": "psychologist"
  },
  "requires_confirmation": false,
  "missing_information": [],
  "confidence": 0.86,
  "response_strategy": "show_options"
}
```

هذه النتيجة للاستخدام الداخلي والتحقق البرمجي فقط. لا نخزن أو نعرض التفكير الحر
للنموذج. كل ادعاء متعلق بالنظام يجب أن يأتي من نتيجة أداة، لا من ذاكرة النموذج.

## 4. البنية المستهدفة باستخدام LangGraph

المشروع يحتوي LangGraph بالفعل، وهو أنسب من حلقة Agent مفتوحة لأنه يفرض عقداً
واضحاً للعقد والانتقالات.

### حالة الرسم

```text
AgentState
├── request_id / conversation_id / user_id
├── authenticated_actor_and_permissions
├── locale / user_message
├── consented_context_scope
├── conversation_summary
├── risk_assessment
├── intent_and_plan
├── pending_confirmation
├── tool_calls / tool_results
├── final_response
└── audit_events
```

### العقد

1. `validate_request`: التحقق من الهوية والصلاحيات ونطاق الموافقة.
2. `safety_gate`: التقاط الخطر الصريح بقواعد حتمية قبل النموذج.
3. `plan_turn`: تحديد المقصد وما إذا كانت هناك معلومات ناقصة أو حاجة إلى أداة.
4. `retrieve_context`: جلب أقل سياق مسموح من الباك إند أو قاعدة المعرفة.
5. `policy_gate`: رفض الأدوات أو المعاملات غير المسموحة حتى لو طلبها النموذج.
6. `confirmation_gate`: إيقاف الرسم وانتظار تأكيد صريح قبل أي كتابة.
7. `execute_tool`: تنفيذ أداة واحدة بعقد Pydantic ومعرّف idempotency.
8. `compose_response`: صياغة رد مبني على نتيجة الأداة أو المعرفة المسترجعة.
9. `output_guard`: منع التشخيص، القرارات الدوائية، وادعاء نجاح عملية لم تنجح.
10. `persist_summary`: حفظ ملخص منقح وسجل تدقيق، لا سلسلة التفكير.

### الانتقالات الحرجة

```text
safety_gate -- urgent --> safety response + human handoff option
plan_turn -- no tool --> compose_response
plan_turn -- read tool --> policy_gate --> execute_tool --> compose_response
plan_turn -- write tool --> policy_gate --> confirmation_gate
confirmation_gate -- confirmed --> execute_tool --> compose_response
confirmation_gate -- denied --> compose_response
output_guard -- rejected --> safe fallback
```

يجب وضع حد أقصى لعدد دورات الأدوات في الطلب الواحد، مثل 3، لمنع الحلقات المفتوحة
والتكلفة غير المتوقعة.

### توزيع النماذج عبر OpenRouter

في مرحلة الـAgent يفضّل فصل مهمتين قابلتين للضبط بدلاً من إجبار نموذج واحد على
كل شيء:

- `planner_model`: حرارة منخفضة ومخرجات منظمة لاختيار المسار والأداة.
- `response_model`: لصياغة الرد الطبيعي بعد توفر الحقائق ونتائج الأدوات.

تضاف إعدادات مثل `OPENROUTER_PLANNER_MODEL` و`OPENROUTER_RESPONSE_MODEL` لاحقاً.
تشغيل نموذج reasoning أو رفع ميزانية التفكير لا يُعتمد لمجرد أنه متاح؛ يجب مقارنة
الدقة، زمن الاستجابة، والتكلفة على مجموعة تقييم عون. الحواجز البرمجية تبقى ملزمة
مهما كان النموذج قوياً.

## 5. سجل الأدوات المقترح

### أدوات قراءة في البداية

- `get_user_support_context`: أهداف الدعم والملخص المصرح، لا السجل الطبي الكامل.
- `search_psychoeducation`: بحث RAG في محتوى راجعه مختصون مع معرفات المصادر.
- `list_specialists`: قائمة مختصين وفق الفلاتر المسموحة.
- `list_available_slots`: المواعيد المتاحة فقط.
- `get_booking_status`: قراءة حالة حجز يملكه المستخدم.

### أدوات كتابة بعد إثبات مرحلة القراءة

- `create_booking`
- `reschedule_booking`
- `cancel_booking`
- `request_human_handoff`

كل أداة كتابة تتطلب:

- مستخدماً موثقاً وصلاحية يفرضها الباك إند.
- تأكيداً صريحاً يحتوي ملخص العملية.
- `idempotency_key` لمنع التكرار.
- نتيجة منظمة توضح النجاح أو الفشل.
- سجل تدقيق لا يحتوي نص المحادثة كاملاً.

لا يُضاف إنشاء تنبيه سلامة أو مشاركة بيانات حساسة كأداة عادية قبل اعتماد سياسة
قانونية وسريرية واضحة تحدد الموافقة، الحالات الاستثنائية، ومن يستقبل التنبيه.

## 6. مراحل التنفيذ

### المرحلة A: Prompted Chatbot — منفذة جزئياً الآن

النطاق:

- فصل السياسة الموثوقة عن بيانات المستخدم.
- خطة دور حتمية لكل رسالة.
- حماية من حقن التعليمات داخل السياق.
- حدود دوائية وتشخيصية وحدود ادعاء تنفيذ الحجز.
- بوابة أزمة حتمية قبل النموذج.

معيار الخروج:

- نجاح مجموعة تقييم عربية تشمل الفصحى واللهجات.
- مرور جميع حالات الأزمة الصريحة المعروفة عبر بوابة السلامة.
- عدم تأكيد أي حجز أو إجراء لم تنفذه أداة.
- عدم تسرب حقول غير مدرجة في نطاق السياق.

### المرحلة B: Read-only Agent

النطاق:

- إنشاء `AgentState` ورسم LangGraph.
- إضافة أدوات البحث المعرفي، المختصين، والمواعيد كأدوات قراءة فقط.
- إضافة مخطط Pydantic لقرار الأداة ونتيجتها.
- تقييد الأدوات من السيرفر حسب صلاحيات المستخدم.

معيار الخروج:

- صفر وصول ناجح لبيانات مستخدم آخر في اختبارات العزل.
- كل معلومة نظامية في الرد قابلة للربط بنتيجة أداة.
- فشل الأداة ينتج رسالة صادقة ولا يتحول إلى نتيجة مختلقة.
- لا تتجاوز الحلقة الحد الأقصى لاستدعاءات الأدوات.

### المرحلة C: Action Agent مع تأكيد بشري

النطاق:

- إضافة الحجز والتعديل والإلغاء وطلب التحويل البشري.
- حفظ `pending_confirmation` بين الرسائل.
- تطبيق idempotency والتدقيق وإعادة المحاولة الآمنة.

معيار الخروج:

- كل عملية كتابة تحتاج تأكيداً حديثاً مطابقاً للعملية.
- تكرار نفس الطلب لا ينشئ عمليتين.
- نجاح وفشل العملية يظهران كما أعادهما الباك إند حرفياً.
- يستطيع المستخدم إلغاء العملية قبل التنفيذ.

### المرحلة D: ذاكرة وإنتاج

النطاق:

- نقل حالة LangGraph والجلسات إلى Redis أو PostgreSQL.
- تلخيص المحادثة مع مدة احتفاظ وحذف محددين.
- مراقبة زمن الاستجابة، التكلفة، أخطاء الأدوات، ومسارات السلامة.
- مراجعة بشرية دورية لعينات منزوعة الهوية وفق سياسة الخصوصية.

معيار الخروج:

- استمرار الجلسة عبر أكثر من نسخة للخدمة وبعد إعادة التشغيل.
- وجود تنبيهات تشغيلية وميزانية تكلفة وحدود معدل.
- اختبارات حمراء دورية للحقن، تسريب البيانات، والحجز الوهمي.

## 7. توزيع المسؤوليات

### باك إند عون

- المصادقة وRBAC وملكية السجلات.
- الموافقات ونطاق البيانات المسموح للنموذج برؤيتها.
- تنفيذ الحجز والتعديل وسجل التدقيق.
- عدم الثقة في اسم أداة أو معامل قادم من النموذج من دون تحقق.

### خدمة AI

- تخطيط الدور واختيار الأداة من قائمة سمح بها الباك إند.
- تقليل السياق وبناء prompt.
- إدارة رسم LangGraph والتأكيدات المعلقة.
- صياغة الرد وحواجز السلامة والتقييمات.

### واجهة المستخدم

- عرض أن المساعد ليس بديلاً عن المختص.
- عرض ملخص واضح قبل تأكيد أي عملية.
- توفير وصول ظاهر للمساعدة البشرية والطوارئ.
- عدم عرض مؤشرات PID أو الإشارات الداخلية كأنها تقييم سريري.

## 8. ملاحظة حول PID وتحليل المشاعر

القيمة الحالية مفيدة كتجربة هندسية لتعديل نبرة الرد، لكنها ليست مقياساً نفسياً
معتمداً ولا يجب استخدامها للتشخيص أو قرار التصعيد. في النسخة القادمة يفضّل:

- إعادة تسميتها داخلياً إلى `conversation_tone_signal`.
- فصل `risk_assessment` الحتمي عنها تماماً.
- عدم عرضها للمستخدم كـ"خطر" أو "حالة نفسية".
- تقييم فائدتها مقابل مصنف عربي مختبر أو مخطط LLM منظم، مع إبقائها غير سريرية.

## 9. ترتيب العمل التالي

1. تعريف عقود أدوات القراءة مع فريق الباك إند.
2. إنشاء `agent_state.py` و`graph.py` من دون أدوات كتابة.
3. ربط قاعدة معرفة مراجعة عبر `search_psychoeducation`.
4. ربط قوائم المختصين والمواعيد بصلاحيات المستخدم.
5. بناء مجموعة تقييم قبل السماح بأي أداة كتابة.
6. إضافة بوابة التأكيد ثم أدوات الحجز تدريجياً.
